# 测试、证据与交付

[English](../en/TESTING.md) · [Português](../pt-BR/TESTES-E-ENTREGA.md) · [中文](../../README.zh-CN.md)

一个有用的结果应当说明测试了哪些字节、使用了哪些数据以及处于何种环境。本指南区分开发参考实现所需的检查，与支持游戏发布所需的测试。

## 开发过程中

运行与本次改动相关的小规模检查：某个 shim 的契约、配方解析器、结构转换、输入序列或合成数据准备。每次调整后都不要运行完整的框架测试套件。不要仅仅为了翻译 README 就重新构建一个已批准的可执行文件。

把失败记录为可检验的假设。反向验证应当说明为什么该修复不适用于别处：例如，在修正某个特定纹理格式的同时保留一个有效的采样器。

## 每个移植的最小测试矩阵

| 阶段 | 能够证明 | 不能证明 |
| --- | --- | --- |
| 源/哈希校验 | 选取的来源与完整性 | 完整授权或玩法 |
| 主机测试 | 在计算机上跑通的契约 | 完整的 Android ABI 或设备 GPU |
| ARM 构建与 ELF 审计 | 架构与声明的依赖 | 物理执行 |
| CPU 模拟 | 在该环境下执行到的路径 | Mali 驱动、物理音频或输入 |
| 第一个真实帧 | 该二进制在该时刻的画面 | 进度、存档或所有场景 |
| 玩法测试 | 明确执行过的操作/场景 | 没有记录流程的完整战役 |
| 干净的 NXExtract 安装 | 用该 ZIP 完成输入准备 | 另一个 APK、配方或软件包 |

## 物理证据

只能使用本次任务授权的设备。启动之前，确认没有同一游戏的其它实例仍在运行，包括可执行文件已被替换的旧进程。不要把移植文件放在保留给固件更新的目录中。

在可插桩的位置，于 present 之前立即测量真实的上下文/drawable 与像素。活跃的音频、一个 PID、上下文创建成功或 `exit 0` 都不能证明图形正常。确凿的黑屏输出或死掉的上下文会使本次测试失效；请保留诊断信息，并只终止那一个确切的进程。

请实际操作启动、菜单、玩法、过场、暂停、音频、输入/上下文、热插拔、存档/读档和退出。报告实际观察到的场景和时长。所有者的反馈可以补充测试数据，但必须与正确的产物绑定。

## 打包前冻结

完成源码、配方、双语文档、授权信息、pin、构建与审计。在移植之外的记录中保存物理上已批准的可执行文件哈希；重新链接或重新构建都需要新的证据。不要把旧 ZIP 改个名字当作新版本。

移植的规范打包工具应当协调最后一轮工作：在创建该 commit 的唯一候选 ZIP **之前**，先完成校验清单/源、准备阶段与验证阶段。不要把这些完整的边界分别执行一次，再在打包流程里重做一遍。若出现故障，收集错误、一并修复，并在下一次尝试之前冻结一个新的 commit。

## 发布内容

检查完整的框架、图形化 NXExtract 与真实配方、五秒的 NXSplash、生成的启动器、准确的清单文件、PT/EN 的 `<port-id>/INSTALLATION.md`、致谢/授权信息以及所需的对应源码。审计所有 Linux ELF 的 GLIBC ≤ 2.30。默认使用系统自带的 SDL，并拒绝误指向私有 SDL 的情况。

审计可执行文件脚本是否依赖外部 `stat` 命令；读取 `/proc/<pid>/stat` 是另一回事。在发布之前执行启动器失败的前置检查。ZIP 内不得包含任何 APK、资源、原始库或已准备好的游戏数据。

## 接受确切的那个候选

创建候选之后，使用完整的输入通过 [NXExtract 测试干净安装](NXEXTRACT.md)，并保留该 ZIP 而不重新生成其字节。请把回执、配方与输出哈希绑定到同一个 ZIP 和可执行文件上。采用旧数据是不够的。请记录已测试和未测试的设备/固件。

当前集合具备源码和主机示例检查；它尚未经过一轮新的 44 款游戏测试。参见 [发布验证](../../publication/VALIDATION.en.md)。将本集合公开仍然需要 NextOS 的批准。
